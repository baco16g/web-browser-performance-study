# UC2 カードの高さ揃えが重い

> この文書の解説と考察は、Claude（Anthropic の AI）が実測の結果をもとに書いたものです。

300枚のカードを並べた一覧で文字サイズを切り替えると、高さを揃え直す間だけ画面が固まります。原因は JavaScript の計算量ではなく、読み書きの順番が引き起こす強制同期レイアウトです。

## 測るもの

| 指標                       | 始点と終点                                                     | 計測の手段               |
| -------------------------- | -------------------------------------------------------------- | ------------------------ |
| `uc02:input-to-next-frame` | 入力イベントから、次フレームのメインスレッドの仕事が終わるまで | `recordNextFrame`        |
| `uc02:change-text-size`    | ハンドラの開始から終了まで                                     | User Timing              |
| `cdp:layout-count`         | 操作の前後のレイアウト回数の差                                 | `Performance.getMetrics` |
| `cdp:layout-ms`            | 操作の前後のレイアウト時間の差                                 | `Performance.getMetrics` |

## 3つの実装の違いは、レイアウトを起こす回数にある

ブラウザはスタイルやレイアウトの計算を、次の描画の直前までまとめて後回しにします。ただし `offsetHeight` のように最新の寸法が必要な値を読むと、その場で計算するしかありません。

遅い実装（`bad`）は、1枚ごとに書き込みの直後に読み取ります。書き込みが直前の計算結果を無効にするので、カードの枚数だけレイアウトが走ります。

```ts
for (const card of cards) {
  card.style.height = 'auto';
  const height = card.offsetHeight; // ここで毎回レイアウトが走る
  heights.push(height);
  card.style.height = `${height}px`;
}
```

分離した実装（`good`）は、書き込みを先に済ませてから読み取りをまとめます。JavaScript が強制するレイアウトは1回で済みます。

```ts
for (const card of cards) {
  card.style.height = 'auto';
}
const heights = cards.map((card) => card.offsetHeight);
```

CSS に任せる実装（`css`）は、グリッドの `align-items: stretch` で高さを揃えます。JavaScript は寸法を読まないので、強制されたレイアウトはありません。実装全体は [equalize.ts](../../src/usecases/uc02-forced-layout/equalize.ts) にあります。

## 手で観察する

1. `npm run build && npm run preview` で本番ビルドを開きます。
2. 一覧から UC2 を開き、DevTools の Performance パネルで CPU を 4倍遅くします。
3. 記録を始めて「文字サイズを切り替える」を押し、記録を止めます。
4. Main トラックで、`click` の下に並ぶレイアウトの数を実装ごとに比べます。

遅い実装では、イベント処理の中に細かいレイアウトが並ぶはずです。パネルの表示名は Chrome の版によって変わります。Forced reflow の表示は版によって場所が違うので、見つからないときは Layout の呼び出し元を確かめてください。

## 自動で測る

```sh
npm run bench -- --scenario uc02 --trace
```

次の表は Apple M1、Chromium 156 のヘッドレス実行、CPU 4倍制限で測った値です。5回の読み込みで、各回とも2回の空打ちの後に5回操作しました。値は中央値で、± の後は四分位範囲です（[生データ](../results/uc02.json)）。

| 指標                        | bad        | good      | css       |
| --------------------------- | ---------- | --------- | --------- |
| 入力から次フレームまで (ms) | 204.2 ±1.1 | 46.3 ±0.6 | 38.3 ±0.2 |
| ハンドラの処理時間 (ms)     | 194.1 ±0.8 | 35.6 ±0.2 | 0.0 ±0.0  |
| レイアウト回数              | 301        | 2         | 1         |
| スタイル再計算の回数        | 301        | 2         | 1         |
| レイアウト時間 (ms)         | 176.1 ±0.4 | 26.9 ±0.2 | 25.9 ±0.4 |
| スタイル再計算の時間 (ms)   | 17.0 ±0.7  | 10.3 ±0.6 | 4.1 ±0.1  |
| JavaScript の実行時間 (ms)  | 3.6 ±1.0   | 1.5 ±0.4  | 0.5 ±0.4  |
| タスクの合計時間 (ms)       | 208.1 ±7.0 | 46.4 ±0.6 | 38.4 ±0.1 |

保存したトレースでも同じ傾向を確かめました。`bad` の Layout イベントは 301 件で、そのうち 300 件に JavaScript の呼び出し元が記録されています。`good` は 2 件のうち 1 件、`css` は 1 件のうち 0 件でした。呼び出し元があるレイアウトが、JavaScript に強制されたものです。

## 結果の読み方

**JavaScript の実行時間だけを見ても原因に届きません。** `bad` のハンドラは 194.1ms かかっていますが、JavaScript の実行時間は 3.6ms です。残りはハンドラの中で強制されたレイアウトとスタイル再計算でした。「JavaScript が重い」と決めつけてコードの計算量を減らしても、この症状は改善しません。

**1回あたりのレイアウトは軽くても、回数が重なると遅くなります。** `bad` のレイアウト時間 176.1ms を 301 回で割ると、1回あたり約 0.6ms です。ブラウザは変更の影響を受けた部分だけを計算し直すので、1回ごとの費用は小さく抑えられています。

**処理の区間だけで実装を比べると判断を誤ります。** ハンドラの処理時間では `css` が `good` より圧倒的に速く見えますが、入力から次フレームまでの差は 8.0ms です。`good` が JavaScript の中で済ませたレイアウトを、`css` は描画の工程で行っているだけで、レイアウトの量はほとんど変わりません。

## 手を動かして確かめる

1. `?count=1000` にして、`bad` と `good` の時間がカードの枚数にどう比例するかを確かめます。
2. `equalizeBatched` の読み取りのループを書き込みのループの前に移し、レイアウト回数がどう変わるかを予想してから測ります。
3. `--cpu 1` と `--cpu 6` で測り、回数の指標が変わらないことと、時間の指標が変わることを確かめます。
4. `good` の結果をベースラインに保存し、わざと読み取りを1回増やして `npm run bench:compare` が検知するかを試します。

## この教材の限界

カードは文字だけで、画像も仮想化もありません。レイアウトの費用を見やすくするために、他の要因を取り除いた状態です。実際の画面では、要素の数やスタイルの複雑さによって1回あたりの費用が変わります。レイアウト回数は CDP で測っているので Chromium の値です。WebKit で測った時間は[ブラウザごとの違いと古い環境](../browser-differences.md)にあります。

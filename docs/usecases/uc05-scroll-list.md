# UC5 スクロールがカクつく

画像の多い一覧をスクロールすると、ときどき止まって見えます。フレーム間隔の指標は1段階目の改善で正常値に達しますが、そこで終わりではありません。ラスタライズや画像のデコードはメインスレッドの外で進むので、トレースを見ないと費用の差が分かりません。

## 測るもの

JavaScript で毎フレーム 24px ずつ、3秒間スクロールします。

| 指標                       | 意味                                       | 計測の手段              |
| -------------------------- | ------------------------------------------ | ----------------------- |
| `uc05:p95-frame`           | フレーム間隔の p95                         | `requestAnimationFrame` |
| `uc05:dropped-frames`      | 落ちたフレームの推定数                     | `requestAnimationFrame` |
| `uc05:decoded-image-bytes` | DOM にある画像をすべて展開したときの大きさ | 幅×高さ×4 の合計        |
| `RasterTask` など          | ラスタライズや画像のデコードの合計時間     | トレースの集計          |

## 6つの実装は1段階ずつ改善を足す

| 実装       | 足した改善                                                                  |
| ---------- | --------------------------------------------------------------------------- |
| `bad`      | なし。スクロール位置を親の state に持ち、毎フレーム全件を再レンダリングする |
| `isolated` | スクロール位置の表示を、該当の要素の書き換えだけにする                      |
| `light`    | 大きな影と `filter` をやめる                                                |
| `sized`    | 表示の大きさに合う 256px の画像を使う                                       |
| `lazy`     | `loading="lazy"` と `decoding="async"` を指定する                           |
| `good`     | 画面の近くの行だけを DOM に置く                                             |

## 結果の読み方

### フレーム間隔は描画の費用を映さない

`isolated` の時点で p95 は 16.7ms になり、落ちたフレームも 0 になりました。この指標だけを見ると、改善はここで完了です。

しかしトレースでは、`light` でラスタライズが 568.3ms から 117.2ms に、`sized` で画像のデコードが 143.3ms から 22.3ms に減っています。どちらも大きな改善ですが、フレーム間隔の値は動きません。ラスタライズとデコードはメインスレッドの外で進み、`requestAnimationFrame` はメインスレッドの様子しか映さないからです。

最初の実装では `bad` にも親の state を入れておらず、全実装の p95 が 16.8ms で差が出ませんでした。重い表現と大きな画像だけでは、この指標に症状が現れなかったわけです。カクつきの原因がメインスレッドの外にあるなら、別の手段で見る必要があります。

### Long Task は 0 件でもフレームは落ちる

`bad` は 1 フレームが約 50ms かかり、Long Task の判定をわずかに下回りました。3秒間の JavaScript の実行時間は 2997.1ms で、メインスレッドはほぼ埋まっています。それでも Long Task は 0 件でした。50ms 未満のタスクが連続する問題は、この指標では見つかりません。

### 遅延読み込みはメインスレッドの仕事を増やす

`lazy` でタスクの合計時間は 155.6ms から 625.7ms に増え、ばらつきも大きくなりました。スクロールの最中に画像の読み込みが始まるからです。展開サイズの見積もりは 250MiB から 35MiB に減りました。メモリと引き換えに、スクロール中の仕事が増えています。

### 仮想化の効果は時間ではなくメモリに出た

`good` では DOM ノードが 7321 から 2281 に減り、画像の見積もりも 8.8MiB になりました。一方で、JavaScript の実行時間は 19.5ms から 87.8ms に増えています。スクロールのたびに行を作り直すからです。フレーム間隔はすでに正常値だったので、この測定で仮想化の価値を示すのはメモリの値です。

実際に画面にある行は5行ほどなので、2281 は予想より多い値です。`Performance.getMetrics` の `Nodes` には回収待ちのノードも含まれると推定しています。

## 計測値だけでは見つからなかった不具合

作っている途中で、値を見ただけでは気づけない問題が3つありました。

- **`good` の一覧が空だった。** 仮想化のライブラリがスクロール要素を受け取れず、行が1つも描かれていませんでした。トレースからラスタライズが消えたことを不審に思って画面を確かめ、気づきました。値は「とても速い」状態です。計測の前に、画面が正しいことを E2E で確かめる必要があります。
- **2回目の計測がタイムアウトした。** 実行中にボタンを `disabled` にするとフォーカスが外れ、次の Enter が届いていませんでした。
- **同じ文字列の書き込みが重かった。** 行番号の表示に毎回 `textContent` を書き込むと、値が同じでも毎フレーム レイアウトとペイントが走りました。変わったときだけ書き込むようにすると、レイアウトは 182 回から 16 回に減りました。

## 手で観察する

1. `npm run build && npm run preview` で本番ビルドを開きます。
2. DevTools の Rendering タブで Paint flashing を有効にして、`bad` と `good` をスクロールします。
3. Layers パネルでレイヤーの数とメモリの見積もりを確かめます。
4. Performance パネルでスクロールを記録し、Raster トラックの仕事量を比べます。

## 手を動かして確かめる

1. `SCROLL_PIXELS_PER_FRAME` を 120 に上げ、`lazy` と `good` で画像が間に合わない様子を画面で確かめます。
2. `good` の `OVERSCAN_ROWS` を 0 と 10 に変え、JavaScript の実行時間と画像の見積もりの関係を確かめます。
3. `light` の `box-shadow` だけを戻し、トレースのラスタライズの時間を測ります。

## この教材の限界

ヘッドレス実行は GPU を使わず、ソフトウェアで描画します。GPU のある環境では、ラスタライズの費用の出方が変わります。CPU 制限がラスタライズのスレッドに効いているかは確かめていません。Worker には効かなかったので（[UC3](uc03-search-input.md)）、同じように効いていない可能性があります。

描画が追いつかず白い領域が見える現象は測っていません。ブラウザに任せたスクロールはコンポジタだけで進むことがあり、この教材の JavaScript によるスクロールとは振る舞いが違います。画像の展開サイズは上限の見積もりで、ブラウザは使わない画像の展開結果を捨てるので、実際のメモリ使用量ではありません。

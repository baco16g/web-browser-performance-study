# 計測を続ける仕組み

> この文書の解説と考察は、Claude（Anthropic の AI）が実測の結果をもとに書いたものです。

一度きりの計測では、次の変更で性能が劣化しても気づけません。このリポジトリでは、CI の予算、同じランナーでの時間の比較、実利用の模擬の3つで計測を続けます。CI の設定は [ci.yml](../.github/workflows/ci.yml) にあります。

## CI で止めるのは回数の指標だけにする

時間の指標はランナーの性能で大きく揺れるので、固定の上限で判定すると誤検知が増えます。一方で、再レンダリングの数やレイアウトの回数は実行環境が変わってもほとんど変わりません。そこで、回数の指標だけを予算として [budgets.ts](../bench/budgets.ts) に置き、超えたら CI を失敗させます。

| シナリオ | 実装   | 指標                     | 上限 |
| -------- | ------ | ------------------------ | ---- |
| UC1      | `good` | 再レンダリングしたタイル | 2    |
| UC1      | `good` | レイアウト回数           | 0    |
| UC2      | `good` | レイアウト回数           | 2    |
| UC2      | `css`  | レイアウト回数           | 1    |
| UC4      | `good` | CLS                      | 0.01 |
| UC6      | `good` | 残ったリスナー           | 0    |
| UC6      | `good` | 残った DOM ノード        | 10   |
| UC7      | `good` | 通信の回数               | 1    |

手元で確かめるときは、測った後に次のコマンドを実行します。

```sh
npm run bench:budget
```

## 時間は同じランナーで基準と比べ、失敗にはしない

プルリクエストでは、基準のコミットと候補のコミットを同じランナーで測り、差を表にして実行結果の要約に残します。判定は [計測ガイド](measurement-guide.md) の回帰の判定と同じです。ランナーの揺れで止まらないよう、この結果では CI を失敗させません。

```sh
npm run bench:compare -- --baseline before.json --candidate after.json --markdown
```

## 実利用の分布を模擬する

ラボの計測は1つの条件の値しか示しません。実際の利用者は端末も回線もばらばらです。`?rum=1` を付けたページは、離れるときに計測値を `sendBeacon` で送ります。[simulate-field.ts](../bench/simulate-field.ts) は、性能の違う3つの分類の利用者を模擬して UC4 を読み込み、届いた値を分布に集計します。

```sh
npm run bench:field -- --sessions 40
```

| 分類     | 割合 | CPU 制限 | 遅延  | 下り    |
| -------- | ---- | -------- | ----- | ------- |
| `fast`   | 60%  | なし     | 20ms  | 50Mbps  |
| `middle` | 30%  | 4倍      | 40ms  | 10Mbps  |
| `slow`   | 10%  | 8倍      | 150ms | 1.6Mbps |

分類の割合と性能は説明のために決めた架空の値で、実際の統計ではありません。

次の表は実装ごとに40セッションずつ模擬した結果です。単位はミリ秒です（[生データ](results/field.json)）。80セッションの320件の計測値がすべて届きました。

| 実装   | 指標 | 全体の p50 | 全体の p75 | 全体の p95 | `slow` の p75 |
| ------ | ---- | ---------- | ---------- | ---------- | ------------- |
| `bad`  | FCP  | 96         | 246        | 924        | 940           |
| `good` | FCP  | 112        | 316        | 1596       | 1605          |
| `bad`  | LCP  | 622        | 1712       | 6513       | 6549          |
| `good` | LCP  | 280        | 748        | 4072       | 4086          |

### p75 は遅い利用者を映さない

`good` の LCP は全体の p75 で 748ms で、良好の目安の 2.5秒を大きく下回っています。しかし `slow` の利用者の LCP は 4086ms です。`slow` は全体の 10% なので、p75 には現れません。全体の値が良くても、一部の利用者が困っていることはあります。分類ごとに分けて見るか、p95 まで見る必要があります。

### ラボで小さな悪化が、遅い利用者では大きくなる

UC4 の条件では、`good` の FCP の悪化は約 70ms でした。`slow` の利用者では 940ms から 1605ms へ 665ms 悪化しています。HTML の段階で始めた画像とデータの取得が JavaScript と帯域を取り合うので、回線が細いほど影響が大きくなります。

LCP は全体で改善しているので、この実装を選ぶ判断はありえます。ただし、FCP の悪化が特定の利用者に集中していることは、1つの条件のラボ計測では分かりません。

### この模擬の限界

分類ごとの値は1台のマシンで作ったもので、ばらつきは実際の利用者よりずっと小さくなります。`slow` は実装ごとに4セッションしかないので、この分類の p95 は参考になりません。INP は操作を行っていないので含みません。抽出は `?rumSample=` で指定できますが、この模擬では全件を送っています。

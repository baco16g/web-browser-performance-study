# 0004 入力から次フレームまでを requestAnimationFrame と高優先度のタスクで近似する

## 状況

入力への応答を測る標準の手段は Event Timing だが、古いブラウザでは使えず、16ms 未満の操作も記録されない。自動計測では、操作の完了を検知する合図も必要になる。

## 決定

`requestAnimationFrame` の中で `scheduler.postTask` に `user-blocking` のタスクを積み、その実行時刻を終点にする。`scheduler` がない環境では `MessageChannel` を使う。始点は `keydown` や `pointerdown` の `timeStamp` にする。Event Timing は使える環境で別の指標として併記する。

## 理由

`requestAnimationFrame` は描画の直前に呼ばれるので、そこで積んだタスクは描画の後に実行される。標準の API だけで動くので、対応の幅が広い。

UC2 の結果では、この値とタスクの合計時間がほぼ一致した（`good` で 46.3ms と 46.4ms）。UC3 では Event Timing の値とも揃った（`bad` で 206.1ms と 208ms）。

## 経緯

最初は `MessageChannel` だけを使っていた。UC3 の `yield` の実装で、Long Task が 0 件で Event Timing も 16ms なのに、この値だけが 126.9ms になった。`scheduler.yield()` の続きの処理は通常のタスクより優先されるので、計測タスクが検索の完了まで実行されなかったと考えられる。`user-blocking` で積むようにして 14.5ms になった。

始点も最初は `input` イベントだった。`input` の `timeStamp` は処理が始まった時刻になるので、メインスレッドが塞がっていた間の待ちが値から抜ける。`keydown` に変え、前のキーの完了を待たずに入力するようにすると、UC3 の `bad` の値は 108.7ms から 206.1ms に増えた。

## 選ばなかった案

- **Event Timing だけを使う:** ブラウザが測る正確な値だが、対応環境に限られる。8ms 単位に丸められ、16ms 未満の値も取れない。
- **`setTimeout(0)` で次のタスクを待つ:** 書き方は簡単だが、遅延の丸めが計測値に混ざり、優先度の問題も解決しない。
- **`requestAnimationFrame` の中で時刻を取る:** 追い越されないが、そのフレームのスタイル計算、レイアウト、描画が値に入らない。

## 制約

メインスレッドの仕事の終わりまでを測る近似で、ラスタライズ、合成、表示装置の遅延は含まない。画面に光が出るまでの時間を測るには、外部のカメラなどが必要になる。

描画の直後に別の入力の処理が割り込むと、値が実際より長くなることがある。UC3 の CPU 制限なしの `bad` では、この値が 69.5ms で、Event Timing は 40ms だった。

次の表示機会まで待つ時間も含むので、値は表示の更新周期より大きく下がらない。UC1 の `transform` と `good` では、タスクの時間が 18.5ms から 12.5ms に減っても、この値は 19.7ms から 17.6ms にしか減らなかった。

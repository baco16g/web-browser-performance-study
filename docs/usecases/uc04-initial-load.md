# UC4 初期表示と操作可能になるまでが遅い

> この文書の解説と考察は、Claude（Anthropic の AI）が実測の結果をもとに書いたものです。

商品一覧を開くと、主要な画像が出て操作できるようになるまでに待たされます。原因は1つではなく、改善を足すたびに待ちの場所が移っていきました。LCP を内訳に分けて読むと、今どこが律速点なのかが分かります。

## 測るもの

| 指標                 | 意味                                               | 計測の手段                 |
| -------------------- | -------------------------------------------------- | -------------------------- |
| FCP                  | 最初に文字や画像が描かれるまで                     | PerformanceObserver        |
| LCP                  | 主要な画像が描かれるまで                           | web-vitals                 |
| 取得開始の遅れ       | 文書の受信から画像の要求までの時間                 | web-vitals の attribution  |
| 画像の受信時間       | 画像の要求から受信完了までの時間                   | web-vitals の attribution  |
| 描画の遅れ           | 画像の受信完了から描画までの時間                   | web-vitals の attribution  |
| CLS                  | 予期しない配置のずれ                               | web-vitals                 |
| `uc04:usable`        | 一覧の最初の範囲が描かれ、操作できるようになるまで | `recordTimeAfterNextFrame` |
| `uc04:list-complete` | 一覧の全件が描かれるまで                           | `recordTimeAfterNextFrame` |

読み込みの計測では、毎回新しいブラウザコンテキストを作り、キャッシュのない状態で1回だけ開きます。通信は遅延 40ms、下り 10Mbps に制限しました。

## 6つの実装は1段階ずつ改善を足す

| 実装       | 足した改善                                                      |
| ---------- | --------------------------------------------------------------- |
| `bad`      | なし。API を順番に呼び、主要画像は 2048px で遅延読み込み        |
| `parallel` | 2つの API を同時に呼ぶ                                          |
| `priority` | 主要画像を遅延読み込みにせず、優先度を上げ、1024px にする       |
| `reserved` | 画像とバナーの領域を先に確保する                                |
| `early`    | HTML の段階で画像とデータの取得を始める                         |
| `good`     | 一覧は最初の 40 行だけ先に描き、残りを `startTransition` で描く |

実装の切り替えは [strategy.ts](../../src/usecases/uc04-initial-load/strategy.ts) にあります。

## 結果の読み方

### 待ちの場所は移るだけで、消えるとは限らない

`early` は画像の取得開始を 916.0ms から 56.4ms まで早めました。860ms 近い改善ですが、LCP は 116ms しか縮んでいません。画像が届いても、2000行の描画がメインスレッドを塞いでいて、描画の遅れが 969.2ms に増えたからです。

LCP の値だけを見ていると、この改善は「効果が小さい」で終わります。内訳を見れば、次の律速点が描画の遅れだと分かります。そこを `good` で段階的な描画に変えると、LCP は 1228.0ms から 744.0ms に縮みました。

### 段階的な描画は仕事を減らしていない

`good` の Long Task は 0 になり、操作できるまでの時間も 737.8ms に縮みました。一方で、全件が描かれるまでの時間は `early` の 1225.0ms より長い 1298.0ms で、タスクの合計時間も増えています。仕事を分けて後ろへ回しただけで、総量は減っていません。何を先に見せるかを決める改善です。

### HTML で取得を始めると FCP が悪化した

`early` では FCP が 240ms から 308ms に遅くなりました。画像とデータの取得が JavaScript の受信と帯域を取り合うためです。Resource Timing の1回の読み込みの例では、`reserved` で 164ms だった JavaScript の受信完了が、`early` では 232ms になりました。差の 68ms は FCP の悪化幅と同じです。

この画面は JavaScript が描くまで何も表示されないので、JavaScript の遅れがそのまま FCP に出ます。文書の中に見出しなどを書いておけば、影響は小さくなるはずです。

### CLS は他の指標と別の軸にある

`reserved` で CLS は 0.160 から 0.000 になりましたが、LCP はほとんど変わりません。領域の確保は速さではなく安定性の改善です。読み込みの時間だけを追っていると見落とします。

### API が速くても、データが大きければ待たされる

サーバーの処理は 100ms ですが、2000件の JSON は 547KB あり、10Mbps の回線では受信に時間がかかります。Resource Timing の例では、要求の開始から受信完了まで 542ms でした。サーバーのログの応答時間だけでは、この待ちは見えません。

## 手で観察する

1. `npm run build && npm run preview` で本番ビルドを開きます。
2. UC4 を開き、DevTools の Network パネルで回線を遅くして、キャッシュを無効にします。
3. `bad` と `early` で、画像の要求が始まる位置をウォーターフォールで比べます。
4. Performance パネルで再読み込みを記録し、LCP の内訳を確かめます。

## 手を動かして確かめる

1. API の件数を `?count=40` に減らし、`bad` の LCP がどこまで縮むかを予想してから測ります。
2. `network` の帯域を 2Mbps に下げ、`early` の FCP の悪化がどう変わるかを確かめます。
3. `INITIAL_ROW_COUNT` を 5 と 500 に変え、操作できるまでの時間との関係を確かめます。
4. `index.html` に見出しの文字を直接書き、FCP がどう変わるかを測ります。

## この教材の限界

`vite preview` は HTTP/1.1 で配信し、圧縮も TLS もありません。通信の遅延はリクエストごとに足されるだけで、接続の確立は再現していません。サーバーサイドレンダリングは扱っていないので、FCP の絶対値は実際のサービスより遅くなる傾向があります。測定は Chromium だけで、WebKit では動作のみを E2E で確認しています。

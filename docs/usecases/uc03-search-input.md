# UC3 絞り込み中に入力が固まる

> この文書の解説と考察は、Claude（Anthropic の AI）が実測の結果をもとに書いたものです。

5万件の商品を絞り込むと、打った文字が画面に出るまでに待たされます。処理を `async` にしただけでは直らず、効果のある方法にも別の費用があります。入力の応答と結果が出るまでの時間を分けて測ると、その違いが見えてきます。

## 測るもの

40ms 間隔で2文字を続けて入力し、連続入力のときの待ちを再現します。前のキーの処理を待たずに次のキーを送るので、メインスレッドが塞がっていると2文字目はキューで待ちます。

| 指標                       | 始点と終点                                             | 計測の手段               |
| -------------------------- | ------------------------------------------------------ | ------------------------ |
| `uc03:input-to-next-frame` | 各キーの `keydown` から次フレームまで。2文字の遅いほう | `recordNextFrame`        |
| `uc03:results-ready`       | 最後のキーの `keydown` から、結果が描画されるまで      | `recordNextFrame`        |
| `browser:long-task-total`  | 50ms を超えたタスクの時間の合計                        | Long Tasks API           |
| `cdp:task-ms`              | メインスレッドのタスクの合計時間                       | `Performance.getMetrics` |
| `uc03:worker-search`       | Worker の中の検索時間                                  | `performance.now()`      |

## 5つの実装

| 実装        | 検索の進め方                                                   |
| ----------- | -------------------------------------------------------------- |
| `bad`       | 入力のハンドラの中で全件を処理する                             |
| `microtask` | 500件ごとに `await Promise.resolve()` を挟む                   |
| `deferred`  | `useDeferredValue` で検索を後回しのレンダリングに回す          |
| `yield`     | 500件ごとに `scheduler.yield()` で明け渡し、古い検索は打ち切る |
| `worker`    | Web Worker で検索し、古い検索の結果は捨てる                    |

実装は [search-runners.ts](../../src/usecases/uc03-search-input/search-runners.ts) にあります。

## 結果の読み方

### Promise で分けても何も変わらない

`microtask` の入力の反映は 208.4ms で、`bad` と同じです。`await` の続きはマイクロタスクとして、描画や次の入力より先に実行されるからです。コードは非同期に見えても、メインスレッドを手放していません。

この実装では、JavaScript の実行時間が 24.6ms と小さく出ました。トレースを見ると、検索の大半は `FunctionCall` の外の `RunMicrotasks` に入っていて、`ScriptDuration` に数えられていません。タスクの合計時間は `bad` とほぼ同じです。指標の名前だけを見て「JavaScript が軽くなった」と判断すると誤ります。

### useDeferredValue は1文字目しか救わない

`deferred` は入力を先に画面へ反映し、検索を後回しのレンダリングで行います。それでも2文字の遅いほうは 52.8ms 待たされ、Long Task も 146.0ms 残りました。React のレンダリングは中断できますが、1つの関数の実行は途中で止められません。検索の実行中に打った2文字目は、検索が終わるまで待ちます。

1文字だけで測ると、この実装は十分速く見えます。連続入力で測る理由はここにあります。

### yield は応答と結果の両方を改善した

`yield` は入力の反映が 14.5ms になり、Long Task もなくなりました。結果が出るまでの時間も 166.8ms から 116.7ms に短くなっています。分割すると普通は処理が遅くなるはずなので、これは意外な結果でした。

理由は古い検索の打ち切りです。`bad` は2文字分の検索を両方最後まで実行しますが、`yield` は2文字目が来た時点で1文字目の検索をやめます。実際、1文字目の検索が2文字目より先に終わる CPU 制限なしの測定では、`bad` の 30.0ms に対して `yield` は 43.4ms で、分割の費用がそのまま表れました（[生データ](../results/uc03-cpu1.json)）。

### Worker の速さは CPU 制限の見かけも含む

`worker` の結果は 51.9ms で最も速く見えますが、この比較は公平ではありません。Worker の中の検索時間は、CPU 制限が4倍でも 18.1ms、制限なしでも 20.9ms で、ほとんど変わりませんでした。CPU 制限はメインスレッドにだけ効いています。

制限なしの測定では、結果が出るまでの時間は `bad` が 30.0ms、`worker` が 29.5ms でほぼ同じでした。Worker は処理を速くするのではなく、メインスレッドを空けて応答性を守る手段です。遅い端末で Worker の中の処理がどれだけ遅くなるかは、この環境では測れません。

### Long Task の件数だけでは足りない

CPU 制限なしの `bad` では、Long Task は 0 件でした。1回の検索が 50ms を超えないからです。それでも連続入力の Event Timing は 40ms で、入力を待たせています。50ms は長いタスクの目安で、これより短ければ問題ないという意味ではありません。

## 計測器を2か所直した

最初の測定では `yield` の入力の反映が 126.9ms で、Long Task が 0 件という結果と矛盾していました。計測タスクが `scheduler.yield()` の続きに追い越されていたためです。また、`input` イベントを始点にしていたので、キューの待ち時間が値から抜けていました。経緯は [ADR 0004](../adr/0004-next-frame-approximation.md) に残しています。

## 手で観察する

1. `npm run build && npm run preview` で本番ビルドを開きます。
2. UC3 を開き、DevTools の Performance パネルで CPU を 4倍遅くします。
3. 記録を始めて検索欄に数文字打ち、記録を止めます。
4. `bad` と `yield` で、Main トラックのタスクの長さと、打った文字が出る速さを比べます。

## 手を動かして確かめる

1. 検索の区切りの `CHUNK_SIZE` を 50 と 5000 に変え、入力の反映と結果が出るまでの時間がどう動くかを確かめます。
2. `createChunkedRunner` の打ち切りを外し、`yield` の結果が出るまでの時間がどう変わるかを測ります。
3. `--cpu 1` と `--cpu 8` で `worker` を測り、`uc03:worker-search` が変わらないことを確かめます。
4. `KEY_INTERVAL_MS` を 200 にして、`deferred` の入力の反映がどう変わるかを予想してから測ります。

## この教材の限界

検索は意図的に重くしてあり、実際のサービスではサーバーに任せる場面も多いはずです。Worker と結果の受け渡しは番号の配列だけなので、大きなデータを渡すときの複製の費用は測っていません。`scheduler.yield()` は Safari などの環境では使えない場合があり、その場合は `MessageChannel` に切り替わります。上の表は Chromium の値です。WebKit で測った時間は[ブラウザごとの違いと古い環境](../browser-differences.md)にあります。

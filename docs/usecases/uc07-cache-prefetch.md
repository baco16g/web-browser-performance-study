# UC7 再表示や詳細表示が遅い

> この文書の解説と考察は、Claude（Anthropic の AI）が実測の結果をもとに書いたものです。

同じ商品をもう一度開いても、毎回読み込みを待たされます。キャッシュの指定を変えると再表示は速くなりますが、速くするほど古い内容を見せる時間が増えます。速さと内容の新しさの交換を、両方測ります。

## 測るもの

新しい商品の詳細を開いて戻り、同じ商品をもう一度開きます。サーバーの処理は 200ms、通信は遅延 40ms、下り 10Mbps です。

| 指標                  | 意味                                           | 計測の手段                        |
| --------------------- | ---------------------------------------------- | --------------------------------- |
| `uc07:first-visit`    | Enter を押してから、初めての詳細が描かれるまで | `recordNextFrame`                 |
| `uc07:revisit`        | Enter を押してから、再表示の詳細が描かれるまで | `recordNextFrame`                 |
| `uc07:transfer-total` | 1回の操作の通信量                              | Resource Timing の `transferSize` |
| `uc07:requests`       | 1回の操作の通信の回数                          | Resource Timing                   |

## 5つの実装

| 実装         | キャッシュの指定     | 足した改善                                  |
| ------------ | -------------------- | ------------------------------------------- |
| `bad`        | `no-store`           | なし                                        |
| `revalidate` | `no-cache` と `ETag` | 変更がなければ 304 を返す                   |
| `fresh`      | `max-age=60`         | 60秒はサーバーに問い合わせない              |
| `memory`     | `max-age=60`         | 取得した結果をアプリのメモリに持つ          |
| `good`       | `max-age=60`         | フォーカスが 150ms とどまったら先に取得する |

## 自動で測る

```sh
npm run bench -- --scenario uc07 --warmup 1 --iterations 3
```

次の表は Apple M1、Chromium 156 のヘッドレス実行、CPU 4倍制限で測った値です。5回の読み込みで、各回とも1回の空打ちの後に3回操作しました。値は中央値で、± の後は四分位範囲です（[生データ](../results/uc07.json)）。

| 指標            | bad        | revalidate | fresh      | memory     | good     |
| --------------- | ---------- | ---------- | ---------- | ---------- | -------- |
| 初回の表示 (ms) | 233.0 ±0.0 | 233.2 ±0.3 | 232.7 ±2.1 | 233.0 ±0.8 | 4.9 ±0.2 |
| 再表示 (ms)     | 233.1 ±0.7 | 209.2 ±0.7 | 21.8 ±12.5 | 4.4 ±0.1   | 4.3 ±0.1 |
| 通信量 (KiB)    | 62.6       | 31.6       | 31.3       | 31.3       | 31.3     |
| 通信の回数      | 2          | 2          | 2          | 1          | 1        |

`fresh` の通信の回数が 2 なのは、キャッシュから返した分も Resource Timing に記録されるからです。2回目の `transferSize` は 0 でした。

サーバーの内容を更新した後に再表示したとき、新しい内容が見えるかは次のとおりです。E2E で固定しています。

| 実装         | 更新が見えるか               |
| ------------ | ---------------------------- |
| `bad`        | 見える                       |
| `revalidate` | 見える                       |
| `fresh`      | 60秒間は見えない             |
| `memory`     | キャッシュにある間は見えない |
| `good`       | キャッシュにある間は見えない |

## 結果の読み方

### 再検証は通信を省かない

`revalidate` の再表示は 233.1ms から 209.2ms で、24ms しか縮みません。サーバーへの問い合わせは毎回行い、省けるのは本文の転送だけだからです。約 31KiB の本文を 10Mbps で受信する時間とほぼ同じ差です。通信量は半分になるので、回線の弱い環境では意味があります。

### メモリのキャッシュは読み込みの表示そのものをなくす

`fresh` の再表示は 21.8ms で速いのですが、ばらつきが大きく、結果は非同期に届きます。`memory` は結果を同期的に取り出せるので、読み込み中の表示を挟まず、4.4ms で描けます。

### 先読みは初回の表示を速くする

`good` の初回の表示は 4.9ms です。フォーカスは次に押される候補を教えてくれるので、押す前に取得を終えられます。測定では通り過ぎただけの項目も混ぜましたが、通信の回数は増えていません。150ms とどまるまで取得を始めないからです。

ただし、この測定はフォーカスがとどまった項目を必ず開くので、先読みが無駄にならない条件です。とどまっただけで開かない場合は、通信とメモリの費用だけが残ります。

### 速さと引き換えに古い内容を見せている

`fresh` 以降の実装は、サーバーの内容が変わっても再表示に反映されません。どれくらい古くてもよいかはデータによって違います。商品の説明なら数分は許容できても、価格や在庫はそうはいきません。表示をキャッシュする場合でも、購入の確定時にはサーバーで確かめる必要があります。

## 作成中に見つかった不具合

詳細から戻ったときに、元の項目へフォーカスが戻りませんでした。一覧を描き直すとボタンの要素が作り変わるので、保存しておいた要素への参照が無効になっていたためです。戻り先を商品の ID で覚えるように直しました。E2E で見つかった不具合です。

## 手で観察する

1. `npm run build && npm run preview` で本番ビルドを開きます。
2. UC7 を開き、DevTools の Network パネルを表示します。
3. 同じ項目を2回開き、Size 列と Status 列の違いを実装ごとに比べます。

## 手を動かして確かめる

1. `PREFETCH_DWELL_MS` を 0 にして項目を次々に移動し、無駄な通信の回数を確かめます。
2. `max-age=60` を `max-age=1, stale-while-revalidate=60` に変え、速さと更新の見え方を確かめます。
3. メモリのキャッシュに有効期限を足し、更新が見えるまでの時間を選べるようにします。

## この教材の限界

Playwright の WebKit では、`max-age` を指定しても `fetch` のたびに全量が転送され、HTTP キャッシュの効果を確かめられませんでした。Safari の挙動とは限りません。性能の測定は Chromium だけです。Service Worker、CDN、bfcache は扱っていません。キャッシュの無効化は、購入の完了のような操作をきっかけに行う設計もあり、ここでは実装していません。

# UC6 画面を行き来するとメモリが増える

> この文書の解説と考察は、Claude（Anthropic の AI）が実測の結果をもとに書いたものです。

一覧と詳細を往復するたびにメモリが増えます。原因を1つ直してもヒープの増加は止まらず、すべての参照の経路を切って初めて止まりました。増えた量だけではリークと判断できないことも、ここで確かめます。

## 測るもの

別々の商品の詳細を開いて一覧へ戻る操作を、10回繰り返します。操作の前後で GC を実行し、回収されずに残った量を測ります。

| 指標                     | 意味                               | 計測の手段               |
| ------------------------ | ---------------------------------- | ------------------------ |
| `cdp:retained-heap`      | 10往復の後に残った JS ヒープ       | `Performance.getMetrics` |
| `cdp:retained-nodes`     | 10往復の後に残った DOM ノード      | `Performance.getMetrics` |
| `cdp:retained-listeners` | 10往復の後に残ったイベントリスナー | `Performance.getMetrics` |

`HeapProfiler.collectGarbage` で GC を強制しないと、回収待ちのオブジェクトが値に混ざります。

## 4つの実装は1段階ずつ改善を足す

詳細画面は、2000件のレビューを含む約 300KiB のデータを持ちます。

| 実装       | 足した改善                                                 |
| ---------- | ---------------------------------------------------------- |
| `bad`      | なし。リスナーも要素の登録も外さず、キャッシュに上限もない |
| `listener` | 画面を離れるときに `resize` のリスナーを外す               |
| `detached` | 画面を離れるときに要素の登録を外す                         |
| `good`     | キャッシュの件数を 20 件までにする                         |

## 自動で測る

```sh
npm run bench -- --scenario uc06 --runs 5
```

次の表は Apple M1、Chromium 156 のヘッドレス実行、CPU 4倍制限で測った値です。5回の読み込みで、各回とも20往復の空打ちの後に10往復を5回行いました。値は10往復あたりの中央値です（[生データ](../results/uc06.json)）。

| 指標                  | bad        | listener   | detached   | good       |
| --------------------- | ---------- | ---------- | ---------- | ---------- |
| 残った JS ヒープ      | 3.0 MiB    | 3.0 MiB    | 3.0 MiB    | -30.7 KiB  |
| 残った DOM ノード     | 460        | 460        | 0          | 0          |
| 残ったリスナー        | 10         | 0          | 0          | 0          |
| タスクの合計時間 (ms) | 124.2 ±1.4 | 122.1 ±5.4 | 126.9 ±4.8 | 111.2 ±5.1 |

## 結果の読み方

### 1つ直しても、別の経路が残っていれば解放されない

`listener` でリスナーの増加は止まりましたが、ヒープは 3.0 MiB ずつ増えたままです。詳細のデータを保持している場所が、リスナーの他にもあるからです。

どの経路がデータを保持しているのかを確かめるため、[strategy.ts](../../src/usecases/uc06-memory-growth/strategy.ts) を一時的に書き換えて、キャッシュの上限と他の改善の組み合わせを測りました。

| キャッシュの上限に足した改善 | 残った JS ヒープ | 残った DOM ノード | 残ったリスナー |
| ---------------------------- | ---------------- | ----------------- | -------------- |
| なし                         | 3.0 MiB          | 460               | 10             |
| リスナーを外す               | 0.0 MiB          | 460               | 0              |
| 要素の登録を外す             | 3.0 MiB          | 0                 | 10             |
| 両方                         | 0.0 MiB          | 0                 | 0              |

データを保持していた経路は、リスナーのクロージャとキャッシュの2本でした。

### 要素の登録はデータを保持していなかった

事前の予想では、登録された要素からも React の内部を通じて詳細のデータがたどれるので、経路は3本だと考えていました。実測では、要素の登録が残っていてもヒープの増加は止まっています。アンマウントのときに React が要素からの参照を切っていると推定しています。

残った 460 個のノードは、JS ヒープの値にはほとんど現れません。ヒープだけを見ていると、このリークは見つかりません。

### 上限のあるキャッシュはリークではない

同じ操作を6回繰り返したときの、GC の後のヒープの推移です（[生データ](../results/uc06-series.json)）。単位は MiB です。

| 実装   | 1回目 | 2回目 | 3回目 | 4回目 | 5回目 | 6回目 |
| ------ | ----- | ----- | ----- | ----- | ----- | ----- |
| `bad`  | 5.8   | 8.9   | 12.0  | 15.0  | 18.0  | 21.0  |
| `good` | 5.8   | 8.9   | 9.0   | 9.0   | 9.0   | 9.0   |

2回目までの2つの実装は同じ増え方です。`good` はキャッシュが上限の 20 件に達すると増加が止まります。短い観察でメモリが増えたからといって、リークとは判断できません。上限に達するまで繰り返して、残り方を比べます。

### 時間の指標には表れない

タスクの合計時間は、どの実装でも大きく変わりません。この規模のリークは、すぐには遅さとして現れません。容量の決まった環境では、ある時点で突然問題になる種類の不具合です。

## 手で観察する

次の手順は Memory パネルの3スナップショット法です。

1. `npm run build && npm run preview` で本番ビルドを開き、UC6 の `bad` を表示します。
2. 「10回往復する」を押してから、ヒープスナップショットを取ります。
3. もう一度押して2枚目を、さらに押して3枚目を取ります。
4. 3枚目で、1枚目と2枚目の間に作られたオブジェクトに絞り込みます。
5. 残っている `Array` や `Detached` の要素を選び、Retainers で保持している経路をたどります。

## 手を動かして確かめる

1. `CACHE_CAPACITY` を 5 と 50 に変え、ヒープが止まる高さを予想してから測ります。
2. `DetailView` に `setInterval` を足して解除せず、タスクの合計時間が時間とともにどう変わるかを確かめます。
3. `detail` を参照しないリスナーに書き換え、`bad` のヒープの増加がどう変わるかを測ります。

## この教材の限界

測っているのは JS ヒープ、DOM ノード、リスナーの数で、画像や描画用のメモリは含みません。GC を強制して測っているので、実際の利用者のヒープの動きとは違います。値は V8 のもので、JavaScriptCore の振る舞いは確かめていません。DevTools の手順は画面で試していません。

# 計測ガイド

このガイドは、ブラウザの性能を測るときの考え方を、このリポジトリの実装に沿って説明します。React で画面を作った経験があり、DevTools の Performance パネルを開いたことがある人を想定しています。初回は「比べられる数字を作る手順」までを通読し、それ以降は必要なときに引いてください。

## 比べられる数字を作る手順

### 最初に始点と終点を決める

「遅い」のままでは測れません。UC2 では、始点を入力イベントの `timeStamp`、終点を次のフレームのメインスレッドの仕事が終わった時点に定めました。始点と終点が決まると、使える道具も決まります。

名前だけで指標を選ぶと、測りたいものとずれます。UC2 のハンドラの処理時間は、CSS に任せる実装で 0.0ms でした。実際には次フレームまでに 38.3ms かかっています。処理の後に行われるスタイル計算とレイアウトが、区間の外にあるからです。

### 同じ条件で測る

`bench/harness.ts` は、次の条件を毎回そろえます。

| 条件           | そろえ方                                    | そろえる理由                   |
| -------------- | ------------------------------------------- | ------------------------------ |
| ビルド         | 本番ビルドを `vite preview` で配信する      | 開発ビルドは別物の性能になる   |
| データ         | 乱数の種を固定した商品データを使う          | データが違うと比較できない     |
| CPU            | `Emulation.setCPUThrottlingRate` で制限する | 速い開発機では問題が隠れる     |
| 画面サイズ     | 1280×720 に固定する                         | レイアウトの量が変わる         |
| ブラウザの状態 | 読み込みごとに新しいコンテキストを作る      | キャッシュと状態を持ち越さない |
| 実行順         | 固定の種で実装の順番を混ぜる                | 発熱などの時間変化が偏らない   |

### 読み込みごとの中央値を1件として扱う

1回の読み込みの中で操作を繰り返すと、値は似たものになります。これらをすべて独立した観測として数えると、件数だけが増え、ばらつきを小さく見積もってしまいます。そこで読み込みごとに中央値を求め、それを1件として集計します。

初回の操作は JIT の準備などで遅くなるので、`--warmup` で指定した回数は結果から除きます。

### 時間と回数を一緒に見る

時間は実行のたびに揺れますが、回数はほとんど揺れません。UC2 のレイアウト回数は、5回の読み込みすべてで同じ値でした。原因の説明には回数が、体感への影響の説明には時間が向いています。

### 読み込みはキャッシュのない状態で1回ずつ測る

UC4 のように読み込みそのものを測るときは、1回の読み込みが1件になります。毎回新しいコンテキストで開くので、キャッシュや接続は持ち越しません。回数は `--runs` で増やします。

### 改善は1つずつ足して測る

複数の改善を同時に入れると、どれが効いたのか分かりません。UC4 と UC5 は、隣り合う実装の差が改善1つになるように並べました。律速点を1つ直すと次の律速点が見える流れは、この並びでなければ確かめられません。

## 計測そのものが結果を変える

計測の道具も、ブラウザの上で動くプログラムです。このリポジトリでは影響を次のように抑えています。

- **HUD:** 自動計測では `?hud=0` で表示を止めます。手動で見るときも、更新を 500ms に間引き、`contain: strict` の箱の中だけを書き換えます。
- **トレース:** 記録の負荷があるので、時間を測る実行とは分けて取ります。
- **Playwright の `click()`:** 位置の確認でレイアウトが起きるので、`Enter` キーで操作します。ボタンには事前にフォーカスを移しておきます。
- **完了の待ち方:** `requestAnimationFrame` でのポーリングはフレームを増やすので、50ms 間隔のタイマーで確認します。

## 計測値は別の測り方と突き合わせる

計測の仕組みにも前提があり、前提が崩れると値がずれます。このリポジトリでは次の5件を実際に踏みました。どれも、別の手段の値と比べたことで気づいています。

| 起きたこと                                                                         | 気づいたきっかけ                                 | 対処                                |
| ---------------------------------------------------------------------------------- | ------------------------------------------------ | ----------------------------------- |
| 描画後の計測タスクが `scheduler.yield()` の続きに追い越され、値が 126.9ms に伸びた | Event Timing は 16ms で、Long Task も 0 件だった | 計測タスクを `user-blocking` で積む |
| `input` イベントの `timeStamp` が処理の開始時刻で、キューの待ちが抜けた            | 連続入力の待ちが値に出なかった                   | 始点を `keydown` にする             |
| Worker の中の処理に CPU 制限が効かなかった                                         | CPU 倍率を変えても Worker の時間が変わらなかった | 比較は制限なしの結果も併記する      |
| `ScriptDuration` に `await` の後の処理が入らなかった                               | 同じ検索なのに `TaskDuration` だけが同じ値だった | 全体の時間は `TaskDuration` で見る  |
| `requestAnimationFrame` の間隔が、描画の重い実装でも 16.7ms のままだった           | トレースのラスタライズの合計が約5倍違った        | 描画の費用はトレースで見る          |

UC3 の修正後は、自作の計測値と Event Timing の値が 206.1ms と 208ms で揃いました。独立した2つの手段が同じ値を示すと、計測値を信頼しやすくなります。

## 回帰は相対、絶対、揺れの3つで判定する

`src/perf/judge.ts` は、候補の中央値が基準より悪化し、次の3つをすべて超えたときに `fail` を返します。半分のしきい値を超えただけなら `warn` です。

- 悪化の割合（既定は時間も回数も 10%）
- 悪化の量（既定は時間が 5ms、回数が 2 回）
- 基準と候補の四分位範囲の大きいほう

割合だけで判定すると、2ms が 2.3ms になる程度の差を悪化と誤認します。量だけで判定すると、値の大きな指標の悪化を見逃します。2つの結果は次のコマンドで比較できます。

```sh
npm run bench:compare -- --baseline before.json --candidate after.json --variant good
```

## 逆引き

| やりたいこと                 | 方法                                                        |
| ---------------------------- | ----------------------------------------------------------- |
| 1回の操作の時間を画面で見る  | ページを開いて右下の HUD を読む                             |
| 同じ操作を繰り返して比べる   | `npm run bench -- --scenario uc02`                          |
| 計測の回数を増やす           | `--runs 10 --iterations 10` を付ける                        |
| CPU の制限を変える           | `--cpu 6` を付ける                                          |
| 遅い理由を時間軸で読む       | `--trace` で保存したファイルを Performance パネルに読み込む |
| 改善前後を判定する           | `npm run bench:compare`                                     |
| ラスタライズなどの合計を見る | `npm run bench:trace-summary -- --scenario uc05`            |
| React の Profiler の値を見る | `npm run bench:profiling -- --scenario uc01`                |
| 別名で結果を残す             | `--label` を付ける                                          |

保存したトレースでは関数名が圧縮されたままです。元の名前を見たいときは、`npm run preview` で配信したページを DevTools で直接記録してください。

## 計測の限界

この環境の値は、対象の端末での値の代わりにはなりません。CPU 制限は全体を一律に遅くする仕組みで、GPU、メモリ帯域、入力経路の違いは再現しません。PC で候補を絞り、最後は対象の端末で確かめる必要があります。

ブラウザによって使える API も違います。`src/perf/observers.ts` は `PerformanceObserver.supportedEntryTypes` で対応を確かめ、HUD は使えない項目に「非対応」と表示します。入力から次フレームまでの計測は、`scheduler.postTask` がない環境では `MessageChannel` に切り替わるので、Event Timing がない環境でも使えます。

Event Timing の値にも制約があります。`duration` は 8ms 単位に丸められ、16ms 未満の操作は記録されません。改善が進むほど記録が欠けるので、短い処理の比較には向きません。

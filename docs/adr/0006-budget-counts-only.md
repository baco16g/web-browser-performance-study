# 0006 CI の予算は回数の指標だけにする

## 状況

性能の劣化を CI で止めたい。ただし手元の計測値は Apple M1 のもので、CI のランナーとは性能が違う。ランナーの性能も実行のたびに揺れる。

## 決定

CI を失敗させる予算は、再レンダリングの数、レイアウトの回数、通信の回数、残ったリスナーのように、実行環境で変わらない指標だけにする。時間は同じランナーで基準と比べ、結果を表に残すだけで失敗にはしない。

## 理由

UC2 のレイアウト回数は、どの読み込みでも同じ値だった。回数の増加は実装の変化を直接示すので、誤検知がほとんどない。UC1 の再レンダリングの範囲や、UC6 のリスナーの解除し忘れのように、劣化の原因そのものを検知できる。

## 選ばなかった案

- **時間の絶対値で判定する:** 分かりやすいが、ランナーの性能に左右される。上限を緩めると検知できず、厳しくすると誤検知が増える。
- **手元の結果を基準に時間を比べる:** 実行環境が違うので比較にならない。
- **同じランナーでの時間の比較で失敗にする:** 環境は揃うが、数回の測定では揺れが残る。専用の安定した実行環境ができるまでは参考の表示にとどめる。

## 制約

回数の予算では、1回あたりの処理が重くなる劣化を検知できない。時間の比較の表を人が見る必要がある。
